The idea

Pose in, keystroke out

The mod's menus already take WASD/arrows, Space/Enter, and Esc/Backspace. Skeleton Key watches the Kinect skeleton the game is already receiving, recognises a small set of deliberate gestures, and synthesises those exact keys — so a dancer can pick a song, confirm, and back out without touching a keyboard or phone.

It ships as a single drop-in Kinect10.dll that sits between the game and whatever real Kinect back-end is in use. It adds a feature; it replaces nothing.

Architecture

One shim, two kinds of user

The same middle layer works whether the skeleton comes from real Kinect hardware or from ItsVexor's webcam emulator. Skeleton Key forwards the eight functions the game imports to a renamed back-end DLL, and taps the one method that carries body data.

Evidence from the binaries

How the hook attaches

Legacy.exe is 32-bit and imports Kinect10.dll by ordinal only — eight functions. ItsVexor's fake DLL exports exactly the same eight, which confirms the surface we need. The game drives the sensor through the INuiSensor COM interface (the fake DLL logs interface-only methods like NuiSkeletonTrackingEnable), so our tap point is the vtable method, not the flat export.

Because there is only ever one process talking to the sensor — the game — the v1 "two apps can't share one Kinect" problem never arises. The recognizer is a passenger on data the game already pulls.

Implementation detail

Shim mechanics

Everything below lives in one x86 DLL built Release | Win32, /MT (static CRT, no redistributable needed). All eight exports are hand-written __stdcall thunks with the exact SDK 1.8 NuiApi.h signatures; none link against Kinect10.lib, they call function pointers resolved from the back-end at runtime.

Startup — lazy, never in DllMain

DllMain only calls DisableThreadLibraryCalls and stores the module handle. LoadLibrary under the loader lock is unsafe, so real init runs behind InitOnceExecuteOnce, triggered by whichever of our eight exports the game calls first:

  1. Resolve the back-end. LoadLibraryW("Kinect10_backend.dll") from our own directory; GetProcAddress all 8 functions by name into a struct of pointers. Null → log fatal, show one message box, let thunks return E_NUI_DEVICE_NOT_CONNECTED.
  2. Load config. kinectnav.ini beside the DLL over the config.h defaults, if present; otherwise run on defaults (nothing is written).
  3. Allocate the frame buffer (below) and create the recognizer thread suspended-idle — it blocks until the first frame is published.

The vtable wrap — fallback only

M1 showed this is not needed: the game calls the flat NuiSkeletonGetNextFrame export directly, so M2 taps the frame inside that thunk (copy after forwarding, de-dup by frame number). The vtable wrap below stays documented as the fallback if a future Legacy build switches to the interface method.

The game would call NuiCreateSensorByIndex(0, &pSensor), then invoke methods on pSensor through its COM vtable. We patch one slot of that shared vtable, once:

// our export, ordinal 6
HRESULT __stdcall NuiCreateSensorByIndex(int i, INuiSensor** ppSensor) {
    EnsureInit();
    HRESULT hr = g_be.NuiCreateSensorByIndex(i, ppSensor);
    if (SUCCEEDED(hr) && *ppSensor && !g_origGetNextFrame) {
        void** vtbl = *reinterpret_cast<void***>(*ppSensor);
        void** slot = &vtbl[SKEL_GETNEXT_SLOT];      // fixed for SDK 1.8
        g_origGetNextFrame = (GetNextFrameFn)*slot;
        DWORD old;
        VirtualProtect(slot, sizeof(void*), PAGE_READWRITE, &old);
        *slot = (void*)&Hook_SkeletonGetNextFrame;
        VirtualProtect(slot, sizeof(void*), old, &old);
    }
    return hr;
}

// runs on the game's Kinect thread
HRESULT __stdcall Hook_SkeletonGetNextFrame(
        INuiSensor* self, DWORD wait, NUI_SKELETON_FRAME* out) {
    HRESULT hr = g_origGetNextFrame(self, wait, out);
    if (SUCCEEDED(hr) && out) g_frames.publish(*out);   // ~2 KB memcpy
    return hr;
}

SKEL_GETNEXT_SLOT is the method's index in INuiSensor, counted from the header — stable for SDK 1.8. M2 verifies it: a wrong slot yields garbage or a bad HRESULT immediately. Fallback if in-place patching proves fragile: return a full proxy object whose vtable forwards every INuiSensor method to the real one. More code, no VirtualProtect.

Our flat export #17 also forwards-and-taps, for the case where the game uses the flat API too; frames are de-duplicated by timestamp so the recognizer never sees one twice.

Frame buffer

Single producer (game Kinect thread), single consumer (recognizer). A small array of 8 NUI_SKELETON_FRAME slots behind an SRWLOCK — 30 Hz, ~2 KB per copy, contention is nil so a lock is simpler than lock-free and safe. Consumer reads the newest slot each tick and drops anything it fell behind on. publish() also signals a condition variable the recognizer waits on, so it never polls.

Teardown

NuiShutdown (#16) and DLL_PROCESS_DETACH: set the stop event, WaitForSingleObject(thread, 500), then forward to the back-end's NuiShutdown. Leave the vtable patch in place (the DLL stays resident) but clear g_origGetNextFrame so a later re-create re-patches. FreeLibrary(backend) only on detach.

Why v0.7 changes the gesture model

Research & redesign

M3's first four builds treated navigation as a motion — a horizontal swipe. Two live findings pushed back: a swipe-per-item is exhausting (test 1), and the hold-to-repeat pose (arm straight out at shoulder height) fatigues fast (test 2). A literature + prior-art pass (Gemini Deep Research, report kept at docs/Kinect Gesture Navigation UI Design.md) converged on a different model, and it lines up with what the tests were already saying.

What the research is good for — and not

Trust: the biomechanics (Consumed Endurance / “gorilla arm” — keep exertion under ~15% of max shoulder torque, elbow near the ribs, load on the torso), the Physical Interaction Zone anchored to skeleton joints (matches our existing SC/HIP torso-unit space), the Midas-touch / asymmetric-hysteresis framing, and swipe-over-dwell (Dance Central — same genre, same sensor — tried dwell-to-click and dropped it).

Verify: the “empirically validated” threshold table is really uncited engineering defaults, several bibliography links are junk, and it never confronts Kinect v1's inferred-hand jitter (its own figure, ±0.1–0.3 m) against its own tight bands (±10 cm dead zone, ±15 cm activation). Every number is treated as provisional, same status as the current config.h values. Decoded numbers and caveats: docs/notes/research-thresholds.md; full redesign breakdown: docs/notes/m3-m4-redesign.md.

SkeletonKeyLab — live tuning without the game

The positional model has far more tunable surface than the swipe machine (dead zone, activation band, hysteresis, engage dwell, filter constants) and the game crashes every 30–120 s. SkeletonKeyLab.exe (built 31 Aug, third solution project) opens the Kinect directly and pumps frames into the same framebuffer / recognizer / gestures / recorder the DLL ships — no game, no drop-in DLL. Dry-run by default (logs gestures); --live injects keys while its own console is foreground; --record writes a .skcap. kinectnav.ini next to the exe overrides thresholds, trace=1 for the hand-signal log. It loads the genuine runtime by absolute path so it isn't shadowed by our proxy in dist\. Go to Legacy.exe only for a final “keys still scroll the carousel and the feel is right” check.

Interaction model — positional nav + ballistic confirm

Gesture vocabulary

Six actions cover menu navigation, all on the coronal plane (X/Y only — hand Z is unusable on v1). Navigation is position within a body-anchored zone; Confirm and Back are the only motions. Nothing is watched until the user engages. All thresholds live in config; the values below are provisional starting points (see research & redesign).

Implementation detail

Recognizer design

Skeleton space

SDK 1.8 gives NUI_SKELETON_FRAME with up to 6 NUI_SKELETON_DATA. Each has a tracking state (NOT_TRACKED / POSITION_ONLY / TRACKED), a tracking ID, and 20 joints as Vector4 in metres, right-handed: +X to the sensor's left, +Y up, +Z out toward the room. A person's raised right hand therefore moves in −X — which is exactly why mirror exists. Per-joint state (NOT_TRACKED / INFERRED / TRACKED) is checked for every joint a detector reads.

Joints used: HAND_L/R (fall back to WRIST_L/R), ELBOW_L/R, SHOULDER_L/R, SHOULDER_CENTER, HIP_CENTER, HIP_L/R, HEAD. Webcam-sourced skeletons fill the same 20 slots but Z is approximate and some joints sit permanently INFERRED — allowed, but they cap a detector's confidence at 0.7.

Choosing the navigator

  1. Candidates = skeletons with state TRACKED. None → recognizer idles, emits nothing, notes "no body".
  2. Score = smallest Position.z (closest); tie-break smallest |Position.x| (most centred).
  3. Sticky: keep the same tracking ID until it is lost for >0.5 s, even if someone else steps closer — stops the cursor ping-ponging between two dancers.

Normalisation & smoothing

Work body-relative so gestures are position- and size-independent. Let SC = shoulder-centre, HC = hip-centre, torso = |SC−HC| (~0.41 m measured on real hardware, M2). A hand's working coordinate is p = (HAND − SC) / torso — dimensionless. Each used joint gets exponential smoothing s = a·raw + (1−a)·s_prev, fast track a = 0.5 for swipe velocity, slow track a = 0.15 for the positional test and baselines. Per-frame dt comes from the frame timestamp, never assumed 33 ms.

v0.7: the positional dead-zone / activation test needs a hand that sits still when the arm is still. The slow EMA is the first cut; if its lag vs. jitter trade-off is bad against real inferred-hand noise (±0.1–0.3 m raw), swap in a 1 Euro filter on that joint. This is the make-or-break for the ±10 / ±15 cm bands — tune it in SkeletonKeyLab first.

Engage-state machine

IDLE_NO_BODY → DISENGAGED → ENGAGED → (nav emits / auto-repeat / confirm / back) → back to DISENGAGED.

  • DISENGAGED — nothing is watched except the engage test: dominant hand y > SPINE.y, |hand.x − SC.x| inside half shoulder-width, held engageDwellMs (600). Exhausted users rest hands on hips or let them hang — they do not hold one hand floating at chest-centre, so this is a clean gate.
  • Engage → latch the slow-smoothed dominant-hand position as origin. Enter ENGAGED.
  • ENGAGED — per axis, d = (hand − origin) / torso. |d| < navDeadZone → nothing. Crossing navActivate → emit one arrow for that axis/direction, then |d| must return inside navDeadZone before the next discrete emit. Both axes past activation → larger |d| wins. Confirm / Back ballistic swipes are also live here, gated on the hand starting near origin and a 500 ms global cooldown.
  • Auto-repeat — hand held past navActivate for repeatDwellMs (500) → re-emit that direction every repeatIntervalMs (333), optional gentle accel to a floor. Ends on return to the dead zone.
  • Disengage — dominant hand y < HIP_CENTER.y, instantly (no dwell). Body lost >0.5 s → IDLE_NO_BODY. First 15 frames after re-acquiring a body are ignored while smoothing settles.

The overlaps to watch: (1) a fast nav correction must not read as a Confirm/Back swipe — hence the “starts near origin, moves inward” gate plus the cooldown. (2) Y-axis positional nav is the weaker one — spine curvature and weight shifts move origin's reference; if the ±15 cm band can't be made reliable after filtering, fall back to a coarser three-zone Y (low / centre / high) where a parked hand repeat-emits. (3) engage dwell vs. a casual hand-raise — 600 ms and the tight X window are the guard; if it still false-engages, add a “hand roughly still” test.

Output

Action → virtual-key from keys config. SendInput with a key-down, keyPressMs (40) hold, key-up. The game polls with GetAsyncKeyState, so VK-based injection is the right call; a scancode variant and a PostMessage(hwnd, WM_KEYDOWN/UP) path (window found by our own PID) are the fallbacks. Keys are sent only while the game window is foreground unless requireForeground:false.

M1 — "Passthrough proxy" task list

Goal: our Kinect10.dll in the game folder, game runs identically, Kinect scoring works, every call logged. No gestures, no input, no vtable patch yet.

  1. Solution + DLL project, Release|Win32, /MT, output name Kinect10.dll.
  2. exports.def with the 8 ordinals (bare names + @N). Confirm with dumpbin /exports that the build shows ordinals 5, 6, 9, 16, 17, 21, 22, 26.
  3. backend.cpp: on InitOnce, LoadLibraryW("Kinect10_backend.dll"), GetProcAddress all 8 by name, assert non-null, log module path + addresses.
  4. exports.cpp: all 8 as __stdcall thunks with exact SDK signatures. Each logs "[call] NuiXxx(...)" and its HRESULT, then tail-calls the back-end pointer. For the two CreateSensor functions, also log the returned INuiSensor* value.
  5. log.cpp: append to SkeletonKey.log beside the DLL, one line per call, HH:MM:SS.mmm tid=... msg, flush each line.
  6. install.bat: back up folder → verify Kinect10.dll is the genuine one (size / version marker) → ren Kinect10.dll Kinect10_backend.dll → copy ours in → copy kinectnav.default.json to kinectnav.json.
  7. Test: launch Legacy.exe → no crash, no missing-DLL error → controller select shows Kinect Sensor, selectable → start a song with the real sensor → scoring and feedback identical to stock → uninstall.bat restores stock.
  8. Exit criteria: 30-minute session, zero regressions vs. stock, log shows NuiGetSensorCount → NuiCreateSensorByIndex (non-null sensor) → a stream of frame calls during play.

M1 answers an M2 question for free: whether the flat NuiSkeletonGetNextFrame (#17) is ever called, or the game only uses the interface method — in which case #17's log stays silent and M2's vtable patch is mandatory, not optional. Either result is fine and tells M2 exactly what to do.

Tooling — two offline harnesses

SkeletonKeyReplay (28 Aug) — a record.flag next to the shim appends every tapped frame to skcap-*.skcap; the replay exe feeds a capture back through the same framebuffer.cpp + recognizer.cpp the DLL ships. --step runs it fast and lossless, --speed N paces from liTimeStamp (the recognizer's clock was moved onto frame.liTimeStamp for this to be faithful). One real capture is banked (~230 s, an 83 s scripted run) — but its gestures are windup-heavy and not how players actually move, so it's mainly a false-positive smoke test.

SkeletonKeyLab (31 Aug) — opens the Kinect directly and pumps live frames into the same pipeline, no game. This is the primary tuning loop for the positional model: real jitter, real inferred-hand behaviour, zero game crashes, kinectnav.ini hot-editable. --live to inject keys, --record to bank a capture. Replay's role shrinks to a regression check on the banked captures.

Consequences (still hold in v0.7): anchor everything on SHOULDER_CENTER + HIP_CENTER; accept Inferred hands (never require Tracked) and smooth hard — the v0.7 positional bands make this even more critical; drop “push to confirm” entirely — hand Z is unreliable even on a real Kinect. Kinect v1 skeleton needs the dancer ≥ 1.2 m back — a walk-up to ~0.9 m produced junk.

History — the swipe model, superseded by v0.7

These builds are what the redesign grew out of — the feedback here (swipe-per-item exhausting, hold-out pose fatiguing) is exactly what the research then addressed. Right hand only (HAND_RIGHT, fallback wrist; Inferred accepted). The gesture model changed twice in response to live feedback:

Known unknowns

Risks & mitigations

Resolved · M1

Frame cadence on menu screens. M1 on real hardware showed a constant ~30 Hz poll on every screen — title, controller select, song list, coach, gameplay — with no stalls. The recognizer will always have fresh frames.

Resolved · M1

Flat export vs. vtable method. M1 confirmed the game calls the flat NuiSkeletonGetNextFrame export directly. No vtable patch, no SKEL_GETNEXT_SLOT to get right — M2 just copies the frame inside the export thunk.

Understood · M3

The game “hard-exits” because it crashes. What M1/M2 read as an abrupt clean exit is Legacy.exe faulting during teardown — see Legacy.exe crashes. The recognizer thread already carries no exit-flush obligation, so nothing to fix; but live test sessions get cut short randomly.

Confirmed · M2

Hand depth (Z) is unreliable — not just for webcam users. M2 showed a real Kinect v1 reports hands as Inferred most of the time, with Z bouncing ~0.3 m frame to frame.

Resolution: “push to confirm” is dropped entirely. Confirm is a ballistic cross-body swipe (pure X/Y). All hand-based detectors accept Inferred joints and smooth hard.

Open · v0.7

Positional bands vs. hand jitter. The redesign's dead zone (±10 cm) is inside the research's own raw-jitter figure (±10–30 cm) and the activation band (±15 cm) barely clears it — ~5 cm of usable hysteresis. Whether a positional model survives real inferred-hand noise at ~2.75 m is unproven.

Mitigation: explicit low-pass (slow EMA first, 1 Euro filter if needed) on the positional joint; tune it in SkeletonKeyLab before anything else. Fallback: widen the bands, or drop to a coarse three-zone scheme per axis (a parked hand repeat-emits) — loses fine control, keeps reliability.

Live-test constraint

The play environment is still unknown and the only test room is cramped — a narrow clear path at marginal distance. Every capture's noise is a pessimistic floor. Provisional M3 thresholds can't be finalised until there's a capture from wherever the community actually plays.

Tuning risk · v0.7

Y-axis positional nav is the weak axis. Spine curvature and weight shifts move the body reference that origin is measured against, so the up/down band drifts more than left/right.

Mitigation: evaluate X and Y independently, larger |d| wins (no diagonals); if the ±15 cm Y band can't be made reliable after filtering, fall back to a coarse three-zone Y (low / centre / high, parked hand repeat-emits).

In M4

Either-hand tracking. Builds 1–4 watched the right hand only. The v0.7 model needs both — dominant hand navigates + confirms, non-dominant hand is Back — so this is no longer deferred; it lands with M4's Confirm/Back work. handedness config picks which is which.

Open question

Where does this actually get played? M2 and the first capture were recorded in a cramped room at marginal distance. If the real setting is a cleared space that noise is pessimistic; if it is that same room, that noise level is the tuning target. Still unanswered.

The record / replay harness is now built, so this matters less for iteration — but the final tuning pass should use a capture from wherever it will really be played.

Note

Two DLL variants ship in ItsVexor's zip. JDLEGACY is x86 and matches this game build; DREYN is x64 for a different 64-bit Legacy build and will not load here. Test against the x86 one.

Prior art on the drive

What "Legacy Sensor by ItsVexor" taught us

It is a webcam-to-Kinect emulator for this exact mod: a PyInstaller bundle running OpenCV + MediaPipe Pose that infers a body skeleton from a normal camera, writes joint frames to shared memory, and serves them to the game through a small replacement Kinect10.dll. Replacing the real DLL is also what unlocks the "Kinect Sensor" choice on the controller screen.

It confirmed two things we were otherwise guessing: the DLL-replacement hook works on this build in the wild, and the exact eight-ordinal export surface. (We assumed the game would use the INuiSensor vtable; M1 showed it calls the flat export instead — simpler for us.) Its shared-memory + events + SRW-lock IPC is a reference if Skeleton Key ever needs its own sensor feed. Collaboration is not being pursued — this is an independent tool.
