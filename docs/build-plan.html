The idea

Pose in, keystroke out

The Just Dance Legacy Offline PC menus already take ←↑→↓, Enter and Esc. Skeleton Key watches the Kinect skeleton the game is already receiving, recognises a small set of deliberate arm poses, and synthesises those exact keys — so a dancer can pick a song, start it, and back out without a keyboard or phone.

It ships as one drop-in Kinect10.dll that sits between the game and the real Kinect runtime. It adds a feature; it replaces nothing.

One shim

How it attaches

Legacy.exe is x86 and imports Kinect10.dll by ordinal only — eight functions. Our DLL exports those eight, forwards every one to the renamed genuine runtime (Kinect10_backend.dll), and taps the one that carries body data.

  • Startup is lazy. DllMain only stores the module handle. Real init runs behind InitOnceExecuteOnce on the first of our eight exports the game calls: resolve the back-end, load kinectnav.ini over the compiled defaults, start the recogniser thread.
  • The tap. M1 proved the game calls the flat NuiSkeletonGetNextFrame export directly, on a dedicated thread, at a constant ~30 Hz on every screen. So the thunk forwards, copies the frame into a single-slot SRWLOCK buffer (de-duped by frame number + liTimeStamp), and signals the recogniser. No COM-vtable patch needed — that path stays documented as a fallback only.
  • The recogniser thread picks the navigator body (closest + centred tracked skeleton, sticky by tracking ID for 500 ms), normalises joints by torso length (|SHOULDER_CENTER − HIP_CENTER|, ~0.41 m), runs the recogniser, and taps keys via SendInput — only while Legacy.exe is foreground. All timing is off the sensor's liTimeStamp, never wall clock, so replay-at-speed is faithful.
  • Uninstall renames the genuine runtime back, byte-identical. dist/install.bat / uninstall.bat do the rename dance with a 15 MB size guard and an .orig-backup.

Verified on every build: dumpbin shows exactly the 8 Nui* ordinals (base 5), machine x86, imports KERNEL32 + USER32 + GDI32 + SHELL32 only (GDI32 is the dev overlay; SHELL32 is SHQueryUserNotificationState, the display-mode probe), and no self-import of Kinect10.dll.

Primary recogniser — nav_model = extend

An air d-pad on your shoulder

Navigation is postural, not motion-based: where your dominant hand sits relative to your dominant shoulder picks the command. No velocity, no swipe-segmentation, no jitter thresholds — the whole class of motion-detection failures (jitter-triggered fires, wave-back, up/down oscillation, countersteer) simply doesn't exist here.

The shoulder joint is the one anchor Kinect v1 tracks rock-solid and that never drifts — so unlike every earlier positional attempt there is no origin to latch or let creep.

  • Park box — home / off. Hand within dpad_park_radius (0.32 torso) of the shoulder. Bend the elbow, the hand comes home. Nothing fires. Asymmetric hysteresis (dpad_park_exit_k 1.35) so the edge doesn't chatter.
  • Clutch. Starts disarmed. Park the hand for dpad_arm_dwell_ms (200) to arm it. It auto-disarms after the hand sits out of park and out of every wedge (arm hanging, dancing, gesturing) for dpad_disarm_ms (1500). Re-arm = park again. It only ever sleeps from the idle state, never mid-gesture. dpad_arm = 0 makes it always-live.
  • Wedges. Once armed and out of park, direction is the angle of the arm, split into four wedges with dead gaps between them. Right = arm out to the reaching side; Left = across the body; Up = arm up; Down = below the shoulder and off to the side. Straight-down is a wide dead wedge — a hanging arm points there, so it is ignored. Distance past the park box doesn't matter: reach however far is comfortable.
  • Fire & repeat. Enter a wedge → the arrow key fires once after a ~100 ms debounce. Keep holding past dpad_repeat_dwell_ms (600) → accelerating auto-repeat (dpad_repeat_first_ms 430 → dpad_repeat_min_ms 200). Return to park, or slide to another wedge, to stop.

Command mode — Enter / Esc

Put your non-dominant hand on the non-dominant shoulder (within dpad_cmd_gate_radius, 0.42 torso — generous, with 1.5× exit hysteresis, because that hand is usually inferred there). While it's held, the dominant-arm wedges are repurposed:

  • reach up or right, hold dpad_cmd_dwell_ms (600) → Enter
  • reach down or left, hold dpad_back_dwell_ms (3000 — Esc is consequential) → Esc
  • both then slow-repeat (dpad_cmd_repeat_ms 700) while held; the overlay shows a CONFIRM 45% / BACK 45% bar filling

Nav is suppressed while gated. Dropping the non-dominant hand mid-hold just stops it — a mode flip while the same wedge is held emits nothing (no stray arrow key).

Why a hanging arm is safe

Three independent guards, and a relaxed arm fails all of them: it's outside the park box but points straight down (dead wedge, so no wedge is entered); the clutch disarms after 1.5 s of that; and Esc additionally can't fire at all without the deliberate hand-on-shoulder pose.

Dev overlay

A layered click-through GDI window draws the d-pad: field square + crosshair, the park box, R / L / U / D labels with the live wedge lit, a hand-position marker (grey parked / cyan nav / magenta command), an ASLEEP/READY banner, a L hand → shoulder 0.34 / 0.42 gate readout, and the action flash. trace = 1 also logs a dpad[] line ~15 Hz.

Fallback recogniser — nav_model = swipe

The older motion model, kept as a fallback

The v0.8 swipe model still ships behind the flag — horizontal/vertical hand swipes for nav, an overhead-raise for Confirm, an arm-down-and-out pose for Back. It went through a long consolidation pass (a code review after the first d-pad idea's precursor):

  • The swipe trigger, segmentation and ballistic-peak gate were moved onto the clean 1€/Savitzky-Golay signal; the dominant-hand EMA was retired.
  • Positional invariants replaced three stacked guards: a swipe must end in its target zone — Up ends raised (and hand above elbow), Down ends low, Left/Right cross the torso midline. A recovery / return-to-park stroke ends near neutral, so it's rejected with no latency and no state.
  • The dead directional reversal guard, the vLock post-swipe lockout and the swipeConfirmFrames delay were all deleted; bug fixes for the Back grace-timeout re-arm, the resync state clear and the log epoch went in.

It works, but the postural d-pad sidesteps the problems this model spent months fighting, so extend is the default.

Conditioning

1€ filter → Savitzky-Golay

Kinect v1 reports the hands as inferred most of the time: ±0.1–0.3 m of jitter, and a single bad frame can read as ~9 m/s. The dominant hand runs through a 1€ filter (filter.h; Casiez et al. — adaptive low-pass, heavy smoothing at rest, opens up during a fast move) for position, and a 5-point Savitzky-Golay polynomial-fit differentiator for velocity. Measured across the replay corpus: every >16 torso/s spike gone, peak velocity roughly halved, at the cost of ~2 frames (~66 ms) of lag. The d-pad model needs mostly the clean position; the swipe model runs its whole path on this.

Tooling

Three ways to test without the game

The game crashes on its own every ~30–120 s, so the loop is: capture short real sessions → tune offline → brief in-game confirmations.

  • SkeletonKeyReplay — record.flag beside the shim appends every tapped frame to skcap-*.skcap; the replay exe feeds a capture back through the same framebuffer + recognizer + gestures the DLL ships. --step is fast and lossless; a kinectnav.ini beside it overrides thresholds with no rebuild.
  • SkeletonKeyLab — opens the Kinect directly and pumps live frames into the same pipeline, no game. Real jitter, real inferred-hand behaviour, zero crashes, hot-editable ini. --live injects keys, --record banks a capture.
  • Synthetic suite (tools/synth/synth_skcap.py) — generates valid .skcap files from scripted hand paths on a rock-steady torso, replays each, and PASS/FAILs against expected key tallies. 21 cases incl. the d-pad set (park / idle-rest / each wedge / command / clutch). The fast regression gate — must stay green on every change.

The path

How we got here

  • M3 swipe (Aug) — left/right then 4-way hand swipes with a state machine. Tiring, and every jitter fix traded one failure for another.
  • Positional redesign (research pass 1–2) — engage-state + dead-zone/activation bands + rate-controlled repeat. Drafted, coded, but the latched-origin drifted and needed creep hacks; abandoned.
  • Signal + consolidation (research pass 3 + a code review) — committed to the 1€/SG signal, replaced the swipe model's guard stack with the end-zone positional invariants, deleted the dead ones. This is the swipe fallback.
  • Air d-pad (now) — a clean postural model: shoulder-centred, park-box clutch, angle wedges, non-dom-hand command gate. First in-game session: “works so much better, got into the dance.”

Design notes and the three Gemini deep-research passes live in docs/notes/ and docs/Kinect Gesture *.md.

Risks

  • watchLegacy.exe crashes on its ownChronic crash-on-exit (+0x3CE1B0) and a recurring mid-session AV at +0x7500F0 around song↔menu transitions — both confirmed in legacy.exe.*.dmp, faulting module legacy.exe, not our DLL. Keep sessions short; tune offline.
  • medKinect v1 at ~2 m in a cluttered roomHands mostly inferred, ±0.1–0.3 m. Shoulder / hip / head rock-solid; elbow moderate; hand Z unusable. The d-pad leans entirely on the reliable joints and on ratios/angles, not absolute distal position.
  • medPlay space still unknownAll tuning is in a cramped test room — a pessimistic floor. Numbers may shift for a real living room; every threshold is an ini key.
  • lowExclusive-fullscreen hides the overlayRun the game windowed / borderless. Handling this cleanly is a next-step item.
  • okAccidental fires while dancingAddressed: the clutch sleeps after 1.5 s idle, the straight-down dead wedge ignores a hanging arm, and Esc needs the deliberate hand-on-shoulder pose.
